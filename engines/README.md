# Second and third engine: COASTAL and GDart

Everything behind the cross-engine results of the paper (Section 5.6, Table 8). The same programs, input ranges and Z3 are run on COASTAL and
GDart, the exploration trees are rebuilt in JPF's definition of a state, and the same estimators are scored with the same aggregation. JPF,
the main engine, is described in `../instrumentation/`.

## Definitions shared by the three engines

- **State.** A branch outcome with at least two feasible sides (in JPF, a choice-generator state). COASTAL's raw path tree also has nodes with
  one feasible side. `build_trees.py` collapses those chains so that node counts are comparable.
- **Work (`actualSubtreeWork`).**
  - JPF: bytecode instructions between the entry of a state and its backtrack.
  - COASTAL: instrumented bytecode instructions from the branch of the state to the end of every run through it.
  - GDart: statement and method-entry executions in the source files of the program (Truffle CPU tracer), summed over the runs through the
    node, including the re-executed prefix. GDart has no per-branch counters.
  - The three units differ, so only rank statistics are compared.
- **Programs.** The programs of `../benchmarks/` whose `<Program>_z3.jpf` has only symbolic `int` parameters. Results are scored on the programs
  whose tree has exactly the node count of JPF. The status of every attempt is in `run_status_*.csv` (`clean`, `not-finished`,
  `abnormal-run`, `gdart-error`).

## Contents

| Path | Content |
|---|---|
| `coastal.patch` | The only changes to COASTAL (https://github.com/DeepseaPlatform/coastal, commit `cfdba3d`): a one-line fix of the Z3 model parser (Z3 4.8.8 and later print models without the `model` keyword) and per-run logging of executed bytecode instructions and branch decisions. |
| `make_run.py`, `run_batch.py` | Prepare and run COASTAL for every benchmark (target method, bounds and parameter count come from the `.jpf` file). `COASTAL_STRATEGY=DF`, `BF` or `RAND`, and `COASTAL_RUNROOT`. |
| `build_trees.py` | Turns the per-run logs of COASTAL into state trees in JPF's format (`COASTAL_RUNROOT=<runs dir> COASTAL_OUTNAME=<data name>`). |
| `runs/` | One folder per program with the source and the compiled classes (`bin/`) used for the static features. |
| `static_features.py`, `compile_bins.py` | Port of the static lookahead of jpf-symbc (control-flow reachability over `javap -c -p` output), so that the six static features can be computed at COASTAL's program counters. `javap` is taken from `PATH` (or the environment variable `JAVAP`). |
| `data/data_coastal2`, `data/data_coastal2_BF` | COASTAL state trees for depth-first and breadth-first search. |
| `data/data_gdart` | GDart state trees. |
| `run_status_data_coastal2.csv`, `run_status_data_coastal2_BF.csv`, `run_status_data_gdart.csv` | How each run ended, with the node counts of the engine and of JPF. |
| `final_table.py` | The estimator rows for JPF depth-first, COASTAL depth-first and COASTAL breadth-first (Table 8). |
| `audit_coastal_attempts.py` | Outcome of every COASTAL attempt (needs the raw COASTAL logs, which are not shipped; its output is `../results/33_coastal_attempts.txt`). |
| `gdart_bin/` | GDart harness: `img/Dockerfile` (Ubuntu 22.04 with Python 3), `run_one.sh` (one program), `executor.sh` (GDart's executor command with the CPU tracer), `sum_counts.py` (work per run). |
| `make_gdart_run.py`, `make_gdart_run_heldout.py`, `run_gdart_batch.py`, `build_gdart_trees.py`, `gdart_candidates.csv` | Harness generation for the corpus and for the nine held-out programs, the batch driver (parallel containers, time limit per program) and the tree construction for GDart. |

The scoring scripts are in `../analysis/` (`cross_engine_replication.py`, `cross_engine_models.py`, `cross_engine_cost_and_cap.py`,
`cross_engine_load_balance.py`). They reuse the main analysis modules unchanged.

## Reproducing the tables from the shipped trees

No engine is needed. From the root of the package:

```
python make_tables.py 8
```

The individual result files (18, 19, 20, 21, 27, 52 and 53) are regenerated by `bash reproduce.sh results`, whose commands list the exact
call of every script.

## Re-running the engines

**COASTAL** (Windows; the batch files are Windows-only). Clone COASTAL at commit `cfdba3d`, apply `engines/coastal.patch` with `git apply`,
and build it (`gradlew installDist`, JDK 11) so that `engines/coastal/build/install/coastal/lib/` exists. Unpack Z3 4.13.4 (x64 Windows
release) to `engines/z3/`. Then run `python run_batch.py` (options `--max-rows`, `--workers`, `--timeout`). For breadth-first search set
`COASTAL_STRATEGY=BF` and `COASTAL_RUNROOT=runs_BF`. Rebuild the trees with `build_trees.py`.

**GDart.** Download the SV-COMP 2023 archive of GDart
(https://gitlab.com/sosy-lab/sv-comp/archives-2023/-/raw/svcomp23/2023/gdart.zip, SHA-256
`dccf51d3455c07de9c759feb2fa62094d29a368aeeaf33b203feca8b03509e63`) and unpack it to `engines/gdart_bin/gdart/`. Build the image with
`docker build -t gdart-env gdart_bin/img`, then run `python run_gdart_batch.py 3 1800` (3 parallel containers, 30 minutes per program; the
container mounts `engines/` as `/w`). Rebuild the trees with `build_gdart_trees.py`.

## Scope

- Of the 116 configurations, 107 use Z3 and nine use Choco (the seven `*_choco` configurations and `PrecisionCompare` and `PrecisionRoundUnscaled`,
  whose only configuration uses Choco). COASTAL runs only Z3 configurations, one per program. 102 of the 107 were attempted. The other five are the
  wider-range variants `ArrayUtilsIndexOf_wideR`, `BellmanFord_wideR`, `EuclideanGcd_wideR`, `InsertionSort_wideR` and `Tsp_wideR`, whose programs were run
  in their default range.
- Trees are compared with JPF only where the node count agrees exactly: 69 programs for COASTAL (68 of them also in breadth-first order)
  and 65 for GDart. The others are listed with their status in `run_status_*.csv`.
- 18 GDart runs are excluded: 17 are `abnormal-run` (for at least one input GDart returns no trace) and one is `gdart-error`.
- GDart's work unit is coarser than bytecode instructions and it has no program counters, so the learned models are not repeated on GDart
  and only the dynamic features exist there.
- The static-feature port counts conditional back-jumps statically, in two variants (with and without them as back edges), because
  `IfInstruction.isBackJump()` of jpf-symbc depends on the runtime value of the condition.
- Results come from GDart of the SV-COMP 2023 archive in an Ubuntu 22.04 container and from COASTAL at the commit above with Z3 4.13.4, on
  one machine.
